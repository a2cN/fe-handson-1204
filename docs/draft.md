# TanStack Query 講座 企画(ドラフト v2)

## 1. 概要

- 持ち時間は45分。前半20分は講義、後半25分はハンズオン。
- 後半は25分で**強制的に切る**。必須は2ミッションとし、1問ごとに全体で区切って丁寧に進める。
- 参加者はエンジニアだが、実力はバラバラ。ヒント資料を見れば全員が解ける作りにする。

## 2. 決定事項

### 2-1. 題材

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **モックAPI + 商品一覧(採用)** | 外部依存がなく、遅延やエラーを意図的に作れる。「一覧→詳細→戻る」でキャッシュの効果を見せやすい | 題材としては平凡 |
| 外部API(天気、ニュースなど) | 本物のデータで見栄えがする | 当日のネットワークやレート制限が不安。遅延の制御ができない |
| TODOアプリ | 軽く、`useMutation` につなげやすい | 一覧と詳細の遷移が弱く、キャッシュの体験が薄い |

- **理由:** 狙いは「戻っても再リクエストされない」体験。再現性と制御のしやすさでモックAPIが最適。
- **あきらめたもの:** 題材そのものの新鮮さ。これは UI の作り込みで補う(2-4)。

### 2-2. ボリュームと進行

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **必須2ミッション + 各ミッション後に全体で区切る(採用)** | 実力差があっても全員が同じ地点に戻れる。時間が読める | 速い人は待つ時間ができる(発展課題で吸収) |
| 必須4〜5項目を各自のペースで進める(旧案) | 速い人は先へ進める | 25分では終わらない人が出る。途中で全体を止めないため、詰まった人を救えない |
| 全員で講師が実演する | 確実に伝わる | 手を動かす体験が減る |

- **理由:** 25分で確実に「できた」を作ることを優先した。
- **あきらめたもの:** 全員が全項目を自力で体験すること。`queryKey` と `queryFn` の解説は前半の講義に移す。

### 2-3. AIの利用

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **口頭と資料への一文で触れるだけ(採用)** | 運用が軽い。実際に使う人が少ない前提と合う | 強制力はない |
| 全面許可 | ルールが単純 | 課題を自力で解く価値が下がる |
| 禁止を明文化して確認する | 狙いが明確 | 確認の手段がなく、運用の手間だけ増える |

- **理由:** 利用者が少ないので、ルールに時間を使わない。
- **あきらめたもの:** 厳密な線引き(補完は可、エージェントは不可、など)。

### 2-4. モックAPIの方式

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **json-server(採用)** | 本物のHTTPサーバーとして動き、仕組みが目に見える。トラブル時に講師が原因を追いやすい | 起動するプロセスが増える(アプリと2つ)。ポート衝突の可能性がある。遅延などの制御は MSW より粗い |
| MSW | 別プロセス不要。コードは本物のAPI呼び出しのまま | Service Worker という見えにくい仕組みが挟まる。講師が仕組みを理解していないと、トラブル時に対応しにくい |
| Vite のミドルウェア | 追加の依存なし | Vite 専用の書き方になる |

- **理由:** 当日のトラブル対応が講師にとって最大のリスクなので、講師が理解している方式を選ぶ。
- **あきらめたもの:** 起動の手軽さ(2プロセスになる)、MSW が持つ細かい制御。
- **対策:**
  - 1コマンドで両方を起動できるようにする(`npm run dev` でアプリとモックAPIを同時に立ち上げる)。
  - json-server は仕様が大きく変わった版があるため、バージョンを固定する。
  - リクエスト回数は、サーバー側ではなく**クライアント側の fetch の薄いラッパーで数える**。表示も同じ場所で行う。
  - 遅延は、同じ fetch ラッパーの中で `await sleep(API_DELAY_MS)` として入れる(後述の 2-4-1)。json-server の機能には頼らない。

- **版の方針(確定):** json-server は **0.17.4 に固定**する(最新版はベータで、`--delay` も削除されているため)。React や TanStack Query など、それ以外のライブラリは**できるだけ最新**にする。
  - Node は、最新の安定版である **26 LTS** にそろえた(`.nvmrc` と `engines` で指定)。`@types/node` も 26 系。参加者は Node 26 以上を入れる必要がある。

#### 2-4-1. 遅延の入れ方

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **fetch ラッパーで `sleep`(採用)** | ソース上の1行で、確実に遅延する。json-server の版に依存しない。リクエスト回数のカウントと同じ場所に置ける。値を1カ所で変えられる | ブラウザの Network タブには、遅延が表示されない(待ちは通信の前に入るため) |
| json-server 0.x の `--delay` オプション | package.json に1フラグ書くだけ。サーバー側の遅延なので、Network タブにも出る | 古い版に固定する必要がある。最新版(1.0.0-beta.15)ではこのオプションが削除されている |
| 最新版 + 自作のミドルウェア | サーバー側の遅延になる | 最新版はベータで、仕様が変わりうる。講師の理解コストが増える |
| ブラウザの DevTools のスロットリング | 追加の実装が不要 | 参加者の操作が増え、遅延が確実に起きない |

- **理由:** 要件は「遅延を確実に起こす」こと。ソースで完結し、版に左右されない方法を選んだ。
- **あきらめたもの:** Network タブで遅延を見せること。講座の中心は画面上の挙動なので、影響は小さい。
- **遅延の長さ:** 3000ms にする。

  | 選択肢 | 良い点 | 悪い点 |
  |---|---|---|
  | 1500ms(当初) | 待ちのストレスが小さい | 「読み込み中」が一瞬で、キャッシュの有無の差を体感しにくい |
  | **3000ms(採用)** | 待ちをはっきり体感でき、キャッシュから即表示されたときとの差が大きい | エラー時の自動再試行で、エラー表示まで約19秒かかる(2-8) |
  | 5000ms 以上 | 差がさらに際立つ | 25分のハンズオンでは、待ち時間が作業の妨げになる |

  - **理由:** 講座の狙いは、キャッシュの効果を体感すること。待ちがはっきり分かる長さを選んだ。
  - **あきらめたもの:** エラー表示の速さ。2-8 のとおりヒントで補う。値は `src/api/client.ts` の `API_DELAY_MS` で1カ所だけ変えればよい。
- **注意:** 参加者が `queryFn` に書く取得処理は、このラッパー経由にする(直接 `fetch` を呼ぶと遅延もカウントも入らない)。ミッション1の出発点のコードと、完成版の両方で、同じラッパーを使う。

### 2-5. UI と Claude Design

- UI は Claude Design で作り込み、「おしゃれな商品一覧」にする。
- そのため、**表示用コンポーネントと取得ロジックを分離する**。参加者が書き換えるのは取得部分だけにして、見た目を差し替えても課題が壊れない構成にする。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **ロジックを先に作り、仮のUIで動かしてから、Claude Design で見た目を作って差し込む(採用)** | 課題の核(ミッションの動作)を先に確定できる。デザインが差し替わっても動作確認の基準がある | 差し込みの手間が後から発生する |
| デザインを先に作ってから、ロジックを合わせる | 見た目のイメージが先に固まる | デザインに引きずられて課題の設計が変わるおそれがある |
| デザインとロジックを並行する | 全体の期間は短くなる | 食い違いが出たとき、どちらを直すか迷う |

- **理由:** この講座の主役は TanStack Query の体験であり、見た目は従である。
- **あきらめたもの:** 最初からデザインの全体像を見ながら進めること。

**Claude Design に渡す条件(依頼の前に確定する):**

- 画面: 商品一覧、商品詳細。
- 表示が必須の状態: ローディング、エラー、データあり。
- 常に表示する要素: **APIリクエスト回数**と、データの取得状態(取得中か、キャッシュからか)。
- データの形(商品の項目)と、コンポーネントの分け方(`ProductList`、`ProductCard`、`ProductDetail` など)。

**差し込むときの注意:**

- デザインの出力形式が、このプロジェクトのスタックと合うかは、実際に出してみないと分からない。合わない場合は Claude Code で変換する。
- 差し込みのあとで、ミッション1と2が仮UIのときと同じ手順で解けるかを、もう一度確認する。

### 2-6. リポジトリの管理

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **`fe-handson-1204` で `git init` し、独立したリポジトリにする(採用)** | 参加者への配布にそのまま使える。oxlint が親の `.gitignore` に邪魔されず動く | 親の `factory` とは別に管理する手間がある |
| 親の `factory` リポジトリで管理する | 管理が1カ所で済む | 親の `.gitignore` が `repos/` を除外しているため、lint が対象ファイルを見つけられない。配布用に切り出す作業が別に要る |

- **理由:** 配布にはどのみち独立したリポジトリが必要。lint が動かない問題も同時に解決する。
- **あきらめたもの:** 親リポジトリでの一元管理。

### 2-7. React の StrictMode

開発モードの StrictMode は、確認のために effect を2回実行する。そのため `fetch + useEffect` 版は、一覧を開くたびにリクエストが **2回** 記録される。`useQuery` 版は重複をまとめるので **1回** になる。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **StrictMode を残し、講義やヒントの話題にする(採用)** | React の標準設定のまま。`useQuery` が重複リクエストをまとめる利点を、数字で見せられる | 「なぜ2回?」で戸惑う人が出うる。ヒント資料での説明が必要 |
| StrictMode を外す | 回数の表示が直感どおりになる | 標準設定から外れ、現実の開発環境と違う |

- **理由:** 現実に近い環境を保ち、二重リクエストを `useQuery` の利点を示す材料として使える。
- **あきらめたもの:** 回数の表示がひと目で分かること。
- **対応:** ヒント資料と、よくあるエラー(疑問)集に「なぜ2回?」を入れる。

### 2-8. エラー時の再試行(retry)

`useQuery` は、失敗すると標準で3回まで再試行する(待ち間隔は1秒、2秒、4秒)。遅延が3秒あるため、エラー表示まで約19秒かかる(3秒 × 4回 + 待ち7秒)。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **設定は標準のままにし、ヒントで説明する(採用)** | TanStack Query の標準の挙動(自動再試行)を学べる。`retry` オプションを知るきっかけになる | ミッション1でエラー表示を試すと、待ち時間が長く「壊れた?」と思われうる |
| `QueryClient` で `retry` を減らす、または 0 にする | すぐにエラー表示になり、迷わない | 標準の挙動が隠れ、本番で戸惑う原因になる |

- **理由:** 自動再試行は TanStack Query の重要な挙動なので、隠さずに学ぶ材料にする。
- **あきらめたもの:** エラー表示をすぐ確認できること。
- **対応:** ミッション1のヒントに「エラー表示まで約20秒かかるのは、自動で再試行しているため」と書き、`retry` オプションも紹介する。

## 4. ミッション

### ミッション1: `useQuery` に置き換える

- 現状は `fetch + useEffect` で実装された商品一覧。これを `useQuery` に置き換える。
- あわせて、ローディングとエラーの表示を `useQuery` の状態で扱う。
- 学ぶこと: `useQuery` の基本、`queryKey`、`queryFn`、`isPending` と `isError`。

### ミッション2: キャッシュを体験する

- 商品詳細へ移動して一覧に戻り、リクエスト回数が増えないことを確認する。
- `staleTime` を変えて、再取得のタイミングがどう変わるかを観察する。
- 学ぶこと: キャッシュ、`staleTime`。

### 発展課題(必須範囲に含めない)

- 検索条件を Query Key に含める。
- TanStack Query Devtools を使う。
- `useMutation` と `invalidateQueries`。

## 5. 教材

- ハンズオン用ページ
- 完成版のサンプルコードを載せた別ページ
- ミッション形式の課題(各ミッションに段階的なヒント付き)
- よくあるエラー集
- 講師向け進行資料

方針: ヒントは3段階にする(方向性 → 使う API → ほぼ答え)。これで、実力差があっても資料だけで解ける状態にする。

## 6. 時間が余った場合と足りない場合

- 余った場合: 完成版サンプルで `fetch + useEffect` との違いを比較解説する。
- 足りない場合: 解説は省略し、サンプルコードを後から確認してもらう。

## 7. 作業計画

1. (済)土台を作る: Vite + React + TypeScript、json-server、1コマンド起動、`npm ci` で動く状態にする(Node のバージョンも固定する)。
2. (済)仮UIで商品一覧(`fetch + useEffect` 版)を作り、リクエスト回数の表示を付ける。遅延とエラー表示の動作は、ブラウザで確認済み。
3. 完成版(`useQuery` 版)を作り、ミッション1と2が成立することを確認する。
4. Claude Design の依頼条件(2-5)を確定し、見た目を作る。
5. 見た目を差し込み、ミッションが同じ手順で解けるかを再確認する。
6. ミッション、ヒント(3段階)、よくあるエラー集、講師向け資料を書く。
7. 予行演習: 教材だけを渡して、初学者の立場で最後まで解けるかを確かめる。別PCでの起動確認も含める。

## 8. 参加者の環境

- 各自のPCのローカル環境で動かす。
- 開始手順は `npm ci` と `npm run dev` の2コマンドにする。
- 必要なもの: 指定バージョンの Node、`package-lock.json`(コミット済み)。
