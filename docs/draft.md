# TanStack Query 講座 企画(ドラフト v2)

## 1. 概要

- 持ち時間は45分。前半20分は講義、後半25分はハンズオン。
- 後半は25分で**強制的に切る**。必須は2ミッションとし、1問ごとに全体で区切って丁寧に進める。
- 参加者はエンジニアだが、実力はバラバラ。ヒント資料を見れば全員が解ける作りにする。

## 2. 決定事項

### 2-1. 題材

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **モックAPI + 商品一覧(採用)** | 外部依存がなく、遅延やエラーを意図的に作れる。「一覧→詳細→戻る」でキャッシュの効果を見せやすい | 題材としては平凡 |
| 外部API(天気、ニュースなど) | 本物のデータで見栄えがする | 当日のネットワークやレート制限が不安。遅延の制御ができない |
| TODOアプリ | 軽く、`useMutation` につなげやすい | 一覧と詳細の遷移が弱く、キャッシュの体験が薄い |

- **理由:** 狙いは「戻っても再リクエストされない」体験。再現性と制御のしやすさでモックAPIが最適。
- **あきらめたもの:** 題材そのものの新鮮さ。これは UI の作り込みで補う(2-4)。

### 2-2. ボリュームと進行

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **必須2ミッション + 各ミッション後に全体で区切る(採用)** | 実力差があっても全員が同じ地点に戻れる。時間が読める | 速い人は待つ時間ができる(発展課題で吸収) |
| 必須4〜5項目を各自のペースで進める(旧案) | 速い人は先へ進める | 25分では終わらない人が出る。途中で全体を止めないため、詰まった人を救えない |
| 全員で講師が実演する | 確実に伝わる | 手を動かす体験が減る |

- **理由:** 25分で確実に「できた」を作ることを優先した。
- **あきらめたもの:** 全員が全項目を自力で体験すること。`queryKey` と `queryFn` の解説は前半の講義に移す。

### 2-3. AIの利用

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **口頭と資料への一文で触れるだけ(採用)** | 運用が軽い。実際に使う人が少ない前提と合う | 強制力はない |
| 全面許可 | ルールが単純 | 課題を自力で解く価値が下がる |
| 禁止を明文化して確認する | 狙いが明確 | 確認の手段がなく、運用の手間だけ増える |

- **理由:** 利用者が少ないので、ルールに時間を使わない。
- **あきらめたもの:** 厳密な線引き(補完は可、エージェントは不可、など)。

### 2-4. モックAPIの方式

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **json-server(採用)** | 本物のHTTPサーバーとして動き、仕組みが目に見える。トラブル時に講師が原因を追いやすい | 起動するプロセスが増える(アプリと2つ)。ポート衝突の可能性がある。遅延などの制御は MSW より粗い |
| MSW | 別プロセス不要。コードは本物のAPI呼び出しのまま | Service Worker という見えにくい仕組みが挟まる。講師が仕組みを理解していないと、トラブル時に対応しにくい |
| Vite のミドルウェア | 追加の依存なし | Vite 専用の書き方になる |

- **理由:** 当日のトラブル対応が講師にとって最大のリスクなので、講師が理解している方式を選ぶ。
- **あきらめたもの:** 起動の手軽さ(2プロセスになる)、MSW が持つ細かい制御。
- **対策:**
  - 1コマンドで両方を起動できるようにする(`npm run dev` でアプリとモックAPIを同時に立ち上げる)。
  - json-server は仕様が大きく変わった版があるため、バージョンを固定する。
  - リクエスト回数は、サーバー側ではなく**クライアント側の fetch の薄いラッパーで数える**。表示も同じ場所で行う。
  - 遅延は、同じ fetch ラッパーの中で `await sleep(API_DELAY_MS)` として入れる(後述の 2-4-1)。json-server の機能には頼らない。

- **版の方針(確定):** json-server は **0.17.4 に固定**する(最新版はベータで、`--delay` も削除されているため)。React や TanStack Query など、それ以外のライブラリは**できるだけ最新**にする。
  - Node は、最新の安定版である **26 LTS** にそろえた(`.nvmrc` と `engines` で指定)。`@types/node` も 26 系。参加者は Node 26 以上を入れる必要がある。

#### 2-4-1. 遅延の入れ方

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **fetch ラッパーで `sleep`(採用)** | ソース上の1行で、確実に遅延する。json-server の版に依存しない。リクエスト回数のカウントと同じ場所に置ける。値を1カ所で変えられる | ブラウザの Network タブには、遅延が表示されない(待ちは通信の前に入るため) |
| json-server 0.x の `--delay` オプション | package.json に1フラグ書くだけ。サーバー側の遅延なので、Network タブにも出る | 古い版に固定する必要がある。最新版(1.0.0-beta.15)ではこのオプションが削除されている |
| 最新版 + 自作のミドルウェア | サーバー側の遅延になる | 最新版はベータで、仕様が変わりうる。講師の理解コストが増える |
| ブラウザの DevTools のスロットリング | 追加の実装が不要 | 参加者の操作が増え、遅延が確実に起きない |

- **理由:** 要件は「遅延を確実に起こす」こと。ソースで完結し、版に左右されない方法を選んだ。
- **あきらめたもの:** Network タブで遅延を見せること。講座の中心は画面上の挙動なので、影響は小さい。
- **遅延の長さ:** 3000ms にする。

  | 選択肢 | 良い点 | 悪い点 |
  |---|---|---|
  | 1500ms(当初) | 待ちのストレスが小さい | 「読み込み中」が一瞬で、キャッシュの有無の差を体感しにくい |
  | **3000ms(採用)** | 待ちをはっきり体感でき、キャッシュから即表示されたときとの差が大きい | エラー時の自動再試行で、エラー表示まで約19秒かかる(2-8) |
  | 5000ms 以上 | 差がさらに際立つ | 25分のハンズオンでは、待ち時間が作業の妨げになる |

  - **理由:** 講座の狙いは、キャッシュの効果を体感すること。待ちがはっきり分かる長さを選んだ。
  - **あきらめたもの:** エラー表示の速さ。2-8 のとおりヒントで補う。値は `src/api/client.ts` の `API_DELAY_MS` で1カ所だけ変えればよい。
- **遅延をかける範囲:** **商品一覧の取得(`fetchProducts`)だけ**にかける。詳細、検索、購入(発展課題)にはかけない。

  | 選択肢 | 良い点 | 悪い点 |
  |---|---|---|
  | すべての API に遅延をかける(当初) | 仕組みが単純 | 発展課題で、詳細・検索・購入のたびに3秒待たされ、作業の妨げになる |
  | **商品一覧の取得だけにかける(採用)** | ミッション1・2の体験は保ちつつ、発展課題は待たずに試せる。どの取得に遅延があるかがコード(`delay: true`)で明示される | 発展1(詳細のキャッシュ)は、待ち時間での差が出ず、リクエスト回数でしか効果が見えない。発展課題でも一覧に戻ると3秒待つ |
  | 画面の欄に「遅延あり/なし」の切り替えを付ける | 講師も参加者も自由に切り替えられる | 操作が1つ増え、切り忘れで体験が変わる |
  | 課題のページだけ遅延、解答例は遅延なし | 解答例がすぐ見られる | 課題と解答例で挙動が変わり、比べられない |

  - **理由:** 遅延の目的は「ミッション1・2で、キャッシュの効果を体感する」こと。目的に必要な場所だけにかける。
  - **あきらめたもの:** 発展1で、待ち時間の差によってキャッシュを体感すること(リクエスト回数で確認する)。
  - **実装:** `apiFetch` に `delay` オプションを追加し、標準は遅延なし。`fetchProducts` だけ `delay: true` を渡す。画面右の欄では、遅延がかかったリクエストに ⏱ を付ける。
- **注意:** 参加者が `queryFn` に書く取得処理は、このラッパー経由にする(直接 `fetch` を呼ぶと遅延もカウントも入らない)。ミッション1の出発点のコードと、完成版の両方で、同じラッパーを使う。

### 2-5. UI と Claude Design

- UI は Claude Design で作り込み、「おしゃれな商品一覧」にする。
- そのため、**表示用コンポーネントと取得ロジックを分離する**。参加者が書き換えるのは取得部分だけにして、見た目を差し替えても課題が壊れない構成にする。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **ロジックを先に作り、仮のUIで動かしてから、Claude Design で見た目を作って差し込む(採用)** | 課題の核(ミッションの動作)を先に確定できる。デザインが差し替わっても動作確認の基準がある | 差し込みの手間が後から発生する |
| デザインを先に作ってから、ロジックを合わせる | 見た目のイメージが先に固まる | デザインに引きずられて課題の設計が変わるおそれがある |
| デザインとロジックを並行する | 全体の期間は短くなる | 食い違いが出たとき、どちらを直すか迷う |

- **理由:** この講座の主役は TanStack Query の体験であり、見た目は従である。
- **あきらめたもの:** 最初からデザインの全体像を見ながら進めること。

**Claude Design に渡す条件(依頼の前に確定する):**

- 画面: 商品一覧、商品詳細。
- 表示が必須の状態: ローディング、エラー、データあり。
- 常に表示する要素: **APIリクエスト回数**と、データの取得状態(取得中か、キャッシュからか)。
- データの形(商品の項目)と、コンポーネントの分け方(`ProductList`、`ProductCard`、`ProductDetail` など)。

**差し込むときの注意:**

- デザインの出力形式が、このプロジェクトのスタックと合うかは、実際に出してみないと分からない。合わない場合は Claude Code で変換する。
- 差し込みのあとで、ミッション1と2が仮UIのときと同じ手順で解けるかを、もう一度確認する。
- `LoadingView`、`ErrorView`、`SearchForm` には、判定用のフック(`useReportListView`、`useReportSearch`)が入っている。見た目を差し替えても、このフックの呼び出しは残す(2-13)。
- Claude Design に頼む画面には、判定パネル(バッジの列、「判定する」ボタン)と、クリアのカードも含める。

### 2-6. リポジトリの管理

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **`fe-handson-1204` で `git init` し、独立したリポジトリにする(採用)** | 参加者への配布にそのまま使える。oxlint が親の `.gitignore` に邪魔されず動く | 親の `factory` とは別に管理する手間がある |
| 親の `factory` リポジトリで管理する | 管理が1カ所で済む | 親の `.gitignore` が `repos/` を除外しているため、lint が対象ファイルを見つけられない。配布用に切り出す作業が別に要る |

- **理由:** 配布にはどのみち独立したリポジトリが必要。lint が動かない問題も同時に解決する。
- **あきらめたもの:** 親リポジトリでの一元管理。

### 2-7. React の StrictMode

開発モードの StrictMode は、確認のために effect を2回実行する。そのため `fetch + useEffect` 版は、一覧を開くたびにリクエストが **2回** 記録される。`useQuery` 版は重複をまとめるので **1回** になる。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **StrictMode を残し、講義やヒントの話題にする(採用)** | React の標準設定のまま。`useQuery` が重複リクエストをまとめる利点を、数字で見せられる | 「なぜ2回?」で戸惑う人が出うる。ヒント資料での説明が必要 |
| StrictMode を外す | 回数の表示が直感どおりになる | 標準設定から外れ、現実の開発環境と違う |

- **理由:** 現実に近い環境を保ち、二重リクエストを `useQuery` の利点を示す材料として使える。
- **あきらめたもの:** 回数の表示がひと目で分かること。
- **対応:** ヒント資料と、よくあるエラー(疑問)集に「なぜ2回?」を入れる。

### 2-8. エラー時の再試行(retry)

`useQuery` は、失敗すると標準で3回まで再試行する(待ち間隔は1秒、2秒、4秒)。商品一覧の取得には遅延が3秒あるため、エラー表示まで約19秒かかる(3秒 × 4回 + 待ち7秒)。遅延のない詳細や検索でも、待ち間隔の分だけ約7秒かかる。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **設定は標準のままにし、ヒントで説明する(採用)** | TanStack Query の標準の挙動(自動再試行)を学べる。`retry` オプションを知るきっかけになる | ミッション1でエラー表示を試すと、待ち時間が長く「壊れた?」と思われうる |
| `QueryClient` で `retry` を減らす、または 0 にする | すぐにエラー表示になり、迷わない | 標準の挙動が隠れ、本番で戸惑う原因になる |

- **理由:** 自動再試行は TanStack Query の重要な挙動なので、隠さずに学ぶ材料にする。
- **あきらめたもの:** エラー表示をすぐ確認できること。
- **対応:** ミッション1のヒントに「エラー表示まで約20秒かかるのは、自動で再試行しているため」と書き、`retry` オプションも紹介する。

### 2-9. 解答例の置き場所

参加者が Git でクローンできるとは限らない(zip などで受け取る可能性がある)。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 別ブランチに置く | 参加者のファイルと混ざらない。差分で比較しやすい | Git を使えない参加者は見られない |
| **同じコードの別ディレクトリ(`src/answers/`)に置き、アプリ内の動くページにする(採用)** | Git 不要。画面のナビから開いて、その場で動作とリクエスト回数を確かめられる | 答えが目に入りやすい |
| 教材ページにだけ載せる | 答えが完全に分かれる | 動く状態で確認できない |

- **理由:** Git の有無に左右されず、全員が動く解答例を見られることを優先した。
- **あきらめたもの:** 答えを見えにくくすること。教材で「まず自分で解く」よう案内する。
- **構成:**
  - `/answers/mission1`(ミッション1の解答)、`/answers/mission2`(ミッション2の解答)。
  - 画面にはリンクを置かず、**URL を直接入力して開く**。URL は教材(ヒントの最終段階や解答のページ)に載せる。

    | 選択肢 | 良い点 | 悪い点 |
    |---|---|---|
    | ヘッダーのナビにリンクを置く | すぐに開ける | 常に目に入り、自力で解く前に開いてしまいやすい |
    | **リンクを置かず、URL の直接入力にする(採用)** | 「見ようと決めた人だけが見る」状態になる。画面もすっきりする | URL を知らないと開けない。教材に必ず載せる必要がある |

    - **理由:** 自力で解くことを促しつつ、Git 不要で動く解答例は残せる。
    - **あきらめたもの:** 解答例へのすぐのアクセス。
  - 解答例ごとに**専用の QueryClient** を持たせた。参加者のページともう一方の解答例とでキャッシュを共有すると、「開いた瞬間に表示される」などの挙動が混ざって比べられなくなるため。
  - 一覧と詳細のリンクは相対パスにして、表示用の部品を課題と解答例で共用している。
  - 定義されていない URL を開いたときは、404ページで解答例の正しい URL を案内する(URL の打ち間違え対策)。

### 2-10. 参加者が編集するファイルの示し方

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| ファイルの先頭コメントだけで示す | 構成を変えずに済む | ファイルが他の場所に混ざり、探す手間がある |
| **編集するファイルを `src/mission/` に集め、先頭に `★` のコメントも付ける(採用)** | 「このフォルダの中だけ」と一言で案内できる。README にも書きやすい | フォルダの意味(機能ではなく役割で分けている)が、通常のプロジェクト構成とは少し違う |
| 編集箇所に `TODO` コメントを入れる | 編集する行まで分かる | 置き換えはファイル全体に及ぶので、行の指定が合わない |

- **理由:** 実力差がある参加者でも、迷わずに編集場所へたどり着けることを優先した。
- **あきらめたもの:** 一般的なプロジェクト構成(`pages/` にページを集めるなど)との一致。
- **案内:** README の「編集するファイル」に、ファイル名と、いつ編集するかの表を載せる。

### 2-11. 商品詳細のキャッシュ

解答例2で一覧から詳細へ移ると、詳細(`/products/4` など)は毎回取得されていた。詳細ページが `fetch + useEffect` のままだったため。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 詳細も必須ミッションに入れる | 「id を key に含める」まで全員が学べる | 25分の必須範囲が増える |
| **解答例の詳細は `useQuery` にし、参加者の詳細は発展課題にする(採用)** | 解答例は全体がキャッシュされ、挙動が一貫する。必須範囲は増えない | 必須だけの人は、詳細が毎回取得される状態のまま終わる |
| 解答例の詳細も `fetch + useEffect` のままにする | 作業が増えない | 解答例2で「キャッシュされないものがある」ように見え、混乱を招く |

- **理由:** 必須の範囲は守りつつ、解答例の挙動を一貫させるため。
- **あきらめたもの:** 全員が詳細のキャッシュまで体験すること。
- **構成:** 解答例の詳細は `src/answers/AnswerProductDetailPage.tsx`。`queryKey` は `['products', id]`。解答例2では一覧と同じく `staleTime: 30_000` を渡す。

### 2-12. 発展課題の範囲

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| A. 商品詳細の1つに絞る | 解答はすでにある。作業が少ない | 速い人が学べる範囲が狭い |
| **B. 4つすべてに出発点と解答を用意する(採用)** | 速い人が長く学べる。事後の自習教材としても使える | 検索UI、更新の操作、Devtools の導入が必要で、作業と保守の量が増える |
| C. 商品詳細と Devtools の2つにする | Devtools は導入が数行で済み、学びが大きい | `useMutation` など更新系は学べない |

- **理由:** 速い人や事後の自習でも、TanStack Query の主要な機能を一通り体験できるようにする。
- **あきらめたもの:** 実装と保守の軽さ。
- **実装上の決定:**

  | 決定 | 選んだもの | 比べたもの | 理由 |
  |---|---|---|---|
  | 解答例の置き場所 | `/answers/advanced` に4つまとめる | 課題ごとに別の URL | 発展4が発展1(詳細)の上に成り立つため、1つのまとまりで動かす必要がある |
  | 更新の題材 | 「購入する」で在庫を1減らす(PATCH) | お気に入り登録、商品の新規作成 | 在庫は一覧にも詳細にも出るので、無効化で両方が更新される様子が見える。追加の画面が要らない |
  | 更新でのデータの扱い | `db.seed.json` を初期データにし、起動のたびに `db.json` を作り直す | `db.json` を直接書き換えたままにする | 購入を繰り返すと在庫が尽き、課題が続けられなくなる。初期データを Git で汚さない |
  | DB の初期化の書き方 | Node のスクリプト(`scripts/reset-db.mjs`) | `cp` コマンド | 参加者が Windows でも動くようにするため |
  | 画面内のリンク | 「基準パス」をコンテキストで渡す(`src/components/scopeBase.ts`) | 相対パス(`../..` など) | 検索ページから詳細へのリンクが、相対パスでは `/search/products/1` になってしまうため |
  | 検索の実行タイミング | フォームの送信時だけ | 入力のたびに検索 | 遅延が3秒あるため、入力のたびだとリクエストが大量に出て、観察しにくい |

### 2-13. 正解の判定と演出

#### 判定の方法

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **A. 画面の動作から判定する(採用)** | 「動いたら正解」で直感的。書き方の違いに強い。追加の道具が要らない。課題用のキャッシュだけを調べられるので、解答例を開いても誤判定しない | 判定のロジックを作り込む必要がある |
| B. テスト(Vitest)で判定する | 実務に近く、判定が厳密 | ターミナルでの操作と準備が増える。演出が地味 |
| C. コードの文字列で判定する | 作るのが簡単 | 書いてあるだけで正解になる。書き方の違いで不正解にもなる |

- **理由:** 参加者の操作を増やさず、実際の動作で正解を確かめられる。
- **あきらめたもの:** テストによる厳密な判定。
- **発展3(Devtools)は判定しない。** Devtools の内部の要素に頼る判定は壊れやすいため。正解条件は問題文には書く。
- **正解条件は、すべての課題で問題文(各ファイルの先頭コメントと README)に書く。**

#### 判定のタイミングと見せ方

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| X. 条件を満たした瞬間に自動で演出する | 驚きが大きい | 意図しないときに出る。何で正解したのか分かりにくい |
| **Y. 「判定する」ボタンで演出する(採用)** | 自分のタイミングで確かめられる。講師が全体に「判定ボタンを押して」と声をかけられる | 操作が1つ増える |
| **Z. 条件のチェックリストを表示する(採用。ただし常には見せない)** | 足りない条件がそのままヒントになる | 常に見えていると、画面の情報が増え、答えを誘導しすぎる |

- **決定:** チェックリストは常には表示せず、「判定する」を押したときの結果としてだけ表示する。
- **あきらめたもの:** 進み具合を常に一目で見られること(バッジで大まかには分かる)。

#### 演出

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| 紙吹雪 | 最も分かりやすい | 何をクリアしたかが伝わらない。ライブラリが増える |
| **クリアのカード(採用)** | 何をクリアしたか、何を学んだかを伝えられる。振り返りを兼ねる | 文面を課題ごとに用意する必要がある |
| **バッジ(採用)** | 課題ごとの達成が並び、発展課題へ進む動機になる | 表示場所が要る |

- **カード:** 課題名、クリアした条件、学んだこと(1行)を載せる。
- **バッジ:** 課題ごとに並べ、クリアすると ✅ が動きながら出てくる。獲得したバッジはブラウザに保存し、再読み込みしても消えない。

#### 判定の対象と条件

| 課題 | 判定条件 |
|---|---|
| ミッション1 | `useQuery` で商品一覧を取得している / 読み込み中の表示が出た / 「エラーを発生させる」をオンにしたとき、エラー表示が出た |
| ミッション2 | 一覧 → 詳細 → 一覧と戻ったとき、一覧のリクエストが増えなかった |
| 発展1 | 商品詳細を `useQuery` で取得している(キーに商品の id を含む) |
| 発展2 | 2種類以上のキーワードで検索し、それぞれ別のキャッシュができた |
| 発展3 | 判定しない(正解条件: 画面に Devtools のボタンが出て、開くとキャッシュの一覧が見える) |
| 発展4 | `useMutation` で購入した / 購入のあと、商品データが取得し直された |

### 2-14. 問題文と資料の置き場所

問題文は、課題ファイルの先頭コメントに書きつつ、1つのファイル(`materials/missions.md`)にもまとめる。

#### ディレクトリ

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **ルート直下に `materials/` を作る(採用)** | 参加者向けの資料だと名前で分かる。企画や講師向けの資料(`docs/`)と混ざらない | ルート直下のディレクトリが1つ増える |
| `docs/` の下に置く(`docs/handson/` など) | 文書が1カ所にまとまる | 講師向けの企画書(`draft.md`)と同じ場所になり、参加者が見てはいけないものと混ざる |
| `src/mission/` の中に置く | 編集するファイルのすぐそばにある | コードと文書が混ざる。「`src/mission/` は編集する場所」という案内と食い違う |

- **理由:** 参加者が読むもの(`materials/`)と、講師が読むもの(`docs/`)を、ディレクトリではっきり分けるため。
- **あきらめたもの:** 文書を1カ所にまとめること。
- **中身:** `materials/missions.md`(問題文)、`materials/README.md`(資料の目次)。技術の解説も、今後ここに追加する。

#### 問題文を2カ所に書くこと

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| コメントだけ | 管理が1カ所で済む | 課題全体を見渡せない。ブラウザやプロジェクターで見せにくい |
| ファイルだけ | 管理が1カ所で済む | 編集中に、別のファイルを開いて確かめる必要がある |
| **両方に書く(採用)** | 編集中も、全体を見渡すときも読める | 内容がずれるおそれがある |

- **理由:** 実力差のある参加者が、どこにいても問題文を読めるようにするため。
- **あきらめたもの:** 管理の手間の少なさ。
- **ずれを防ぐ工夫:** コメントとファイルの項目(画面、今の状態、やること、ヒント、正解条件)をそろえる。どちらかを直したら、もう一方も直す。README には正解条件を重ねて書かず、`materials/missions.md` へのリンクにする。

### 2-15. 「今やること」の表示

テストプレイの前の時点で「ゲームとしてわかりにくい」という声があった。まず、今やることを画面に載せる。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **右側の判定パネルの一番上にカードを出す(採用)** | 判定ボタンやバッジと同じ場所で、目標から判定までの流れが一目で分かる。課題の画面を邪魔しない | 欄の幅が狭く、長い文は折り返す |
| 左側(課題の画面)の上に帯で出す | 一番目立つ | 商品一覧が下に押し下げられる。解答例の画面との見え方が変わる |
| 問題文ファイルへのリンクだけ出す | 作るのが簡単 | 画面を離れないと何をするか分からず、わかりにくさが解消しない |

- **理由:** 「目標 → 操作 → 判定」の流れを1カ所にまとめるため。
- **あきらめたもの:** 画面の中で一番目立つ位置。
- **中身:** 何番目の課題か(必須か発展か)、課題名、ひとことの目標、編集するファイル、判定の前にする操作の手順。
- **今やることの決め方:** まだクリアしていない最初の課題を自動で選ぶ。バッジを押すと、その課題のカードに切り替わる。判定でクリアすると、次の課題に進む。全部クリアすると、発展3(判定なし)を案内する。
- **2-13 との関係:** 条件の達成状況(✅/⬜)は、引き続き「判定する」を押したときだけ出す。カードに出すのは、やることと操作の手順だけ。

### 2-16. 解答例の関数名

解答例を課題ファイルに写したとき、関数名(`Mission1ProductListPage` など)まで写ると、`App.tsx` が読み込めずに画面が真っ白になった。

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **解答例の関数名を、課題ファイルと同じにする(採用)** | 写してもそのまま動く | `App.tsx` では別名で読み込む必要がある |
| よくあるエラー集に載せる | コードを変えずに済む | 起きてから調べることになり、画面が真っ白で原因にたどり着きにくい |

- **理由:** 失敗そのものを起こさないようにするため。
- **あきらめたもの:** `App.tsx` の読み込みの分かりやすさ。
- **残る注意:** 解答例の詳細ページは、購入ボタンを `./AnswerPurchaseButton` から読み込んでいる。ファイルを丸ごと写すと、この読み込み先だけは直す必要がある。よくあるエラー集に入れる。

## 4. ミッション

### ミッション1: `useQuery` に置き換える

- 現状は `fetch + useEffect` で実装された商品一覧。これを `useQuery` に置き換える。
- あわせて、ローディングとエラーの表示を `useQuery` の状態で扱う。
- 学ぶこと: `useQuery` の基本、`queryKey`、`queryFn`、`isPending` と `isError`。

### ミッション2: キャッシュを体験する

- まず、ミッション1の状態で商品詳細へ移動し、一覧に戻る。一覧は**すぐ表示される**(キャッシュ)が、リクエスト回数は**増える**(裏で再取得している。`staleTime` の標準値が 0 のため)。
- 次に `staleTime` を設定し、同じ操作をする。設定した時間内なら、リクエスト回数が**増えない**ことを確認する。
- 学ぶこと: キャッシュ、`staleTime`。

### 発展課題(必須範囲に含めない)

4つすべてに、出発点のコードと動く解答例を用意する(2-12)。1 → 4 の順に進める想定。

| # | 課題 | 編集するファイル | 出発点の状態 | 解答のポイント |
|---|---|---|---|---|
| 発展1 | 商品詳細を `useQuery` に置き換える | `src/mission/ProductDetailPage.tsx` | `fetch + useEffect`。開くたびに取得し直す | `queryKey: ['products', id]`。商品ごとにキャッシュが分かれる(2-11) |
| 発展2 | 検索条件を Query Key に含める | `src/mission/SearchPage.tsx` | `useQuery` だが、キーにキーワードがない。**検索しても結果が変わらない** | `queryKey: ['products', 'search', keyword]` |
| 発展3 | TanStack Query Devtools を使う | `src/mission/DevtoolsSetup.tsx` | 何も表示しない | `<ReactQueryDevtools buttonPosition="bottom-left" />` を返す |
| 発展4 | `useMutation` と `invalidateQueries` | `src/mission/PurchaseButton.tsx` | 普通の関数で購入。**在庫は減るが、表示が古いまま** | `useMutation` で購入し、成功時に `invalidateQueries({ queryKey: ['products'] })` |

- 発展2と発展4は、出発点を「わざと壊れた状態」にしている。直す動機がはっきりし、何が起きているかを観察する学びになる。
- 発展4は、一覧と詳細が `useQuery` になっていることが前提(キャッシュがなければ、無効化の効果が見えない)。
